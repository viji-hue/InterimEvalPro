Question
Compare ApplicationContext and BeanFactory. When would you use each, and what is the difference in how they load beans (eager vs lazy loading)?
Trainee answer
df
Model answer
ApplicationContext uses eager loading — creates ALL beans at startup when container is initialized. Best for production because errors are detected immediately. BeanFactory (deprecated) uses lazy loading — creates beans only when getBean() is called. ApplicationContext is recommended for all modern Spring applications because it supports events, AOP, internationalization, and provides clear error messages at startup. BeanFactory is legacy and should be avoided. Use ApplicationContext = new ClassPathXmlApplicationContext(bean.xml).

Question
What is a Spring Bean and how does IoC (Inversion of Control) differ from traditional object creation? Provide a code example showing both approaches.
Trainee answer
dfg
Model answer
A Spring Bean is any Java object created, configured, and managed by the Spring IoC container. Traditional approach: you create objects using 'new' and manage their lifecycle. IoC approach: Spring creates beans based on configuration (XML, annotations, or Java config) and injects dependencies automatically. Example traditional: Employee e = new Employee(); vs Spring: <bean id='emp' class='Employee'/> then Employee e = context.getBean(Employee.class). IoC removes tight coupling, makes testing easier, and centralizes object management.

Question
What is the difference between tight coupling and loose coupling? Show how dependency injection solves the tight coupling problem with a concrete example.
Trainee answer
dfg
Model answer
Tight coupling: Class directly depends on a concrete class (e.g., Vehicle.move(Bus bus)). Changes to Bus force changes to Vehicle. Loose coupling: Class depends on an interface (e.g., Vehicle.move(Transport t)). Any Transport implementation (Bus, Car, Bike) can be plugged in without modifying Vehicle. Dependency Injection achieves loose coupling by letting Spring inject the dependency, not the class itself. This makes code extensible, testable (easy to mock), and maintainable.
Detailed explanation
SCENARIO: Payment processing system that currently only accepts credit card payments but must support PayPal, Apple Pay, etc. without modifying existing code.\n\nTIGHTLY COUPLED APPROACH (BAD):\n```java\npublic class CreditCard {\n public void processPayment(double amount) {\n System.out.println('Charging ' + amount + ' to credit card');\n }\n}\n\npublic class OrderService {\n private CreditCard creditCard = new CreditCard(); // ← HARDCODED dependency\n \n public void checkout(Order order) {\n creditCard.processPayment(order.getTotal()); // ← Can ONLY use CreditCard\n }\n}\n```\n\nPROBLEM: To add PayPal support, you must modify OrderService — violates Open/Closed Principle.\n\nLOOSELY COUPLED APPROACH (GOOD):\n```java\n// Step 1: Define a contract (interface)\npublic interface PaymentGateway {\n void processPayment(double amount);\n}\n\n// Step 2: Implementations\npublic class CreditCard implements PaymentGateway {\n @Override\n public void processPayment(double amount) {\n System.out.println('Charging ' + amount + ' to credit card');\n }\n}\n\npublic class PayPal implements PaymentGateway {\n @Override\n public void processPayment(double amount) {\n System.out.println('Charging ' + amount + ' via PayPal');\n }\n}\n\n// Step 3: Depend on interface, not concrete class\npublic class OrderService {\n private PaymentGateway paymentGateway; // ← Interface, not CreditCard\n \n @Autowired // Spring injects the implementation\n public OrderService(PaymentGateway paymentGateway) {\n this.paymentGateway = paymentGateway;\n }\n \n public void checkout(Order order) {\n paymentGateway.processPayment(order.getTotal()); // Works with ANY PaymentGateway\n }\n}\n\n// bean.xml\n<bean id='gateway' class='com.payment.PayPal'/> <!-- Switch to PayPal easily -->\n<bean id='orderService' class='com.order.OrderService'>\n <constructor-arg ref='gateway'/>\n</bean>\n```\n\nTOMORROW: To add Apple Pay, just create a class ApplePay implements PaymentGateway. OrderService needs ZERO changes. This is the power of loose coupling + DI.

Question
Explain the Singleton design pattern and how Spring applies it by default to all beans. When would you need to change this behavior and use prototype scope instead?
Trainee answer
mn
Model answer
Singleton pattern ensures only one instance of a class is created and shared across the application. Spring creates all beans as singletons by default — when you call getBean() multiple times, Spring returns the SAME object instance from memory. You need prototype scope when: (1) beans hold request-specific data (user sessions), (2) beans maintain internal mutable state that shouldn't be shared, or (3) you need a fresh object per getBean() call for stateful beans like form objects. Use scope='prototype' in XML or @Scope('prototype') with annotations.
Detailed explanation
SCENARIO: E-commerce application needs a SessionCart bean to store user shopping carts and an InventoryService for checking stock (stateless).\n\nSINGLETON PROBLEM:\n```java\n// User A logs in\nSessionCart cartA = context.getBean(SessionCart.class);\ncartA.addItem('Laptop', 1);\n\n// User B logs in — BUT gets the SAME bean!\nSessionCart cartB = context.getBean(SessionCart.class);\ncartB.addItem('Mouse', 5);\n\nSystem.out.println(cartA == cartB); // true — SAME OBJECT!\nSystem.out.println(cartA.getItems()); // ['Laptop', 'Mouse'] — WRONG! User A's cart is polluted\n```\n\nSOLUTION: Make SessionCart a Prototype Bean\n```xml\n<!-- bean.xml -->\n<bean id='cart' class='com.store.SessionCart' scope='prototype'/>\n```\n\nNOW:\n```java\nSessionCart cartA = context.getBean(SessionCart.class); // Creates NEW instance\ncartA.addItem('Laptop', 1);\n\nSessionCart cartB = context.getBean(SessionCart.class); // Creates DIFFERENT new instance\ncartB.addItem('Mouse', 5);\n\nSystem.out.println(cartA == cartB); // false — DIFFERENT objects\nSystem.out.println(cartA.getItems()); // ['Laptop'] — Correct!\nSystem.out.println(cartB.getItems()); // ['Mouse'] — Correct!\n```\n\nCOMPARISON:\n| Aspect | Singleton | Prototype |\n|--------|-----------|-----------|\n| Instances | 1 per container | New per getBean() |\n| Memory | Low | Higher |\n| Best for | Stateless (services, DAOs) | Stateful (user sessions, forms) |\n| Thread-safe | ⚠ Requires care | ✓ Natural (each thread gets own) |

Question
Explain the three ways to configure Spring beans (XML-based, annotation-based, and Java-based). When would you choose each approach, and show code examples for all three?
Trainee answer
[Skipped]
Model answer
1. XML-based: Define beans in bean.xml using <bean> tags. Best for legacy projects. 2. Annotation-based: Use @Component, @Autowired, @ComponentScan in bean.xml. Modern, reduces XML. 3. Java-based: Use @Configuration class with @Bean methods, no XML at all. Most type-safe and IDE-friendly. Choose Java-based for new projects for full type safety; use XML for legacy; use annotations for balance. All three achieve the same result but differ in configuration style and IDE support.
Detailed explanation
SCENARIO: Building an employee management system with Department and Employee beans.\n\nAPPROACH 1: XML-BASED CONFIGURATION\n```xml\n<!-- bean.xml -->\n<bean id='dept' class='com.company.Department'>\n <property name='deptId' value='10'/>\n <property name='deptName' value='Engineering'/>\n</bean>\n\n<bean id='emp' class='com.company.Employee'>\n <property name='empId' value='101'/>\n <property name='department' ref='dept'/> <!-- Inject Department -->\n</bean>\n```\n\nLoad it:\n```java\nApplicationContext context = new ClassPathXmlApplicationContext('bean.xml');\nEmployee emp = context.getBean(Employee.class);\n```\n\nBEST FOR: Legacy projects, non-Java developers, external configuration.\n\nAPPROACH 2: ANNOTATION-BASED CONFIGURATION\n```xml\n<!-- bean.xml — minimal, just enable scanning -->\n<context:annotation-config/>\n<context:component-scan base-package='com.company'/>\n```\n\n```java\n@Component\npublic class Department {\n @Value('10')\n private int deptId;\n @Value('Engineering')\n private String deptName;\n}\n\n@Component\npublic class Employee {\n @Value('101')\n private int empId;\n \n @Autowired\n private Department department; // Auto-injected\n}\n```\n\nLoad it:\n```java\nApplicationContext context = new ClassPathXmlApplicationContext('bean.xml');\nEmployee emp = context.getBean(Employee.class);\n```\n\nBEST FOR: Modern projects, reduced XML boilerplate, clear intent with @Component, @Service, @Repository.\n\nAPPROACH 3: JAVA-BASED CONFIGURATION (NO XML)\n```java\n@Configuration\n@ComponentScan('com.company')\npublic class AppConfig {\n \n @Bean\n public Department department() {\n Department dept = new Department();\n dept.setDeptId(10);\n dept.setDeptName('Engineering');\n return dept;\n }\n \n @Bean\n public Employee employee() {\n Employee emp = new Employee();\n emp.setEmpId(101);\n emp.setDepartment(department()); // Manual injection in @Bean\n return emp;\n }\n}\n```\n\nLoad it:\n```java\nApplicationContext context = new AnnotationConfigApplicationContext(AppConfig.class);\nEmployee emp = context.getBean(Employee.class);\n```\n\nBEST FOR: Greenfield projects, full type safety, IDE auto-completion, all config in Java code.\n\nCOMPARISON TABLE:\n| Feature | XML | Annotation | Java Config |\n|---------|-----|-----------|-------------|\n| Config location | bean.xml file | XML + Java | Java only |\n| Type safety | ✘ No | ⚠ Partial | ✓ Full |\n| IDE support | ✘ Limited | ⚠ Good | ✓ Excellent |\n| Boilerplate | ✓ High | ⚠ Medium | ✓ Low |\n| Learning curve | ✘ Steep | ⚠ Medium | ✓ Easier |\n| Recommended | ✘ Avoid | ✓ Good | ✓ Best |
